1. VISIÓN GENERAL DE LA ARQUITECTURA
================================================================================

Este es un backend empresarial J2EE (Java Enterprise Edition) construido con
Spring Boot 3.2.1 que proporciona:

✓ Autenticación y Autorización con JWT (JSON Web Tokens)
✓ Base de datos relacional con PostgreSQL y Hibernate/JPA
✓ Control de roles (USER y ADMIN)
✓ Auditoría de cambios en entidades
✓ Logging de acciones de usuarios
✓ CORS habilitado para Angular frontend
✓ Documentación automática con Swagger/OpenAPI
✓ Validación de entrada con Bean Validation
✓ Manejo global de excepciones

Patrón Arquitectónico: Arquitectura de Capas (Layered Architecture)
- Capa de Presentación (Controllers)
- Capa de Lógica de Negocio (Services)
- Capa de Acceso a Datos (Repositories)
- Capa de Seguridad (Security Components)

3. FLUJO DE AUTENTICACIÓN JWT (Paso a Paso)
================================================================================

FLUJO DE LOGIN:
━━━━━━━━━━━━━━━━━

1. Usuario envía credenciales (username/password)
   POST /api/auth/login
   {
     "username": "admin",
     "password": "1234"
   }

2. AuthController recibe la solicitud
   └─> AuthService.login(LoginRequest) procesa

3. AuthService hace:
   a) Autentica con AuthenticationManager
      - Busca usuario en BD por username
      - Valida que la contraseña coincida (BCrypt)
      - Si es correcto, crea Authentication object
   
   b) Genera JWT token (con JwtTokenProvider)
      - Subject: userId
      - Claims: username, roles
      - Firmado con HMAC-SHA256
      - Expira en 24 horas
   
   c) Crea Refresh Token
      - Token aleatorio de UUID
      - Guardado en BD con expiry (7 días)
      - Se usa para renovar access token
   
   d) Registra acción en auditoría
      - Crea AuditLog con LOGIN action
      - Guarda timestamp, IP, usuario, etc.

4. Respuesta al cliente
   {
     "accessToken": "eyJhbGci...",
     "refreshToken": "uuid-token",
     "userId": 2,
     "username": "admin",
     "roles": ["ROLE_ADMIN"]
   }

5. Cliente (Angular) almacena tokens en localStorage

FLUJO DE REQUESTS PROTEGIDOS (Cómo llega el JWT):
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

1. Frontend envía request con header
   GET /api/admin/users
   Authorization: Bearer eyJhbGci...

2. Spring recibe request
   ├─> CorsFilter: Valida origen CORS
   └─> JwtAuthenticationFilter (OncePerRequestFilter)
       ├─ Extrae JWT del header "Authorization"
       ├─ Valida firma del JWT (getSigningKey())
       ├─ Extrae userId del subject
       ├─ Carga UserDetails de BD con CustomUserDetailsService
       ├─ Crea UsernamePasswordAuthenticationToken
       ├─ Guarda en SecurityContextHolder
       └─ Pasa al siguiente filtro

3. Request llega a SecurityFilterChain
   ├─> @PreAuthorize("hasRole('ADMIN')") intercepta
   ├─> Verifica que authentication.roles contiene ROLE_ADMIN
   └─> Si no tiene el rol → 403 Forbidden

4. Si tiene rol, llega a AdminController.getAllUsers()
   └─> Ejecuta la lógica del endpoint

5. Response retorna al cliente

FLUJO DE REFRESH TOKEN:
━━━━━━━━━━━━━━━━━━━━━

1. Access token expira (24 horas)
2. Frontend detecta error 401
3. Frontend envía refresh token
   POST /api/auth/refresh
   {
     "refreshToken": "uuid-token"
   }
4. AuthService valida y genera nuevo access token
5. Frontend recibe nuevo token y lo guarda

4. ESTRUCTURA DE CAPAS

CAPA 1: PRESENTACIÓN (Controllers)
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
Ubicación: controller/

AuthController (@RestController)
├─ POST /api/auth/login
│  └─> Recibe LoginRequest, retorna JwtResponse
├─ POST /api/auth/refresh
│  └─> Recibe RefreshTokenRequest, retorna nuevo JWT
└─ POST /api/auth/logout

AdminController (@RestController, @PreAuthorize("hasRole('ADMIN')"))
├─ GET /api/admin/users?page=0&size=10&sortBy=id&sortDir=ASC
│  └─> Retorna Page<UserDTO>
└─ GET /api/admin/audit-logs?page=0&size=10&sortBy=id&sortDir=ASC

UserController (@RestController)
└─ GET /api/users/{id}
   └─> Retorna UserDTO (usuario autenticado)


CAPA 2: LÓGICA DE NEGOCIO (Services)
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
Ubicación: service/

AuthService
├─ Responsabilidad: Manejar autenticación
├─ Métodos:
│  ├─ login(LoginRequest) - Autentica usuario, genera JWT

│  ├─ logout(String) - Invalida refresh tokens
│  └─ createRefreshToken(Long) - Crea nuevo refresh token

UserService
├─ Responsabilidad: Lógica de usuarios

└─ Usa: UserRepository, UserMapper

AuditLogService
├─ Responsabilidad: Registrar acciones de usuarios
├─ Métodos:
│  ├─ logAction(username, action, entity, ...) - Registra acción
│  └─ getAllAuditLogs(Pageable) - Obtiene logs con paginación
└─ Usa: AuditLogRepository, AuditLogMapper


CAPA 3: ACCESO A DATOS (Repositories)

CAPA 4: SEGURIDAD (Security Components)
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
Ubicación: security/

JwtTokenProvider (@Component)
├─ Responsabilidad: Crear y validar JWT
├─ Métodos:
│  ├─ generateToken(Authentication) - Crea JWT
│  ├─ generateTokenFromUsername(String, Long, String) - Genera desde datos
│  ├─ getUserIdFromToken(String) - Extrae userId del JWT
│  ├─ getValidationStatus(String) - Valida y retorna estado
│  └─ validateToken(String) - Valida firma
├─ Usa: JJWT library + HMAC-SHA256
└─ Propiedades:
   ├─ jwt.secret = clave de firma (64 caracteres)
   ├─ jwt.expiration = 24 horas (86400000 ms)
   └─ jwt.refresh-expiration = 7 días (604800000 ms)

JwtAuthenticationFilter extends OncePerRequestFilter
├─ Responsabilidad: Intercepta requests y valida JWT
├─ Método: doFilterInternal(HttpServletRequest, ..., FilterChain)
│  ├─ Extrae JWT del header "Authorization: Bearer xxx"
│  ├─ Valida JWT
│  ├─ Carga UserDetails de BD
│  ├─ Crea Authentication token
│  └─ Lo guarda en SecurityContextHolder
└─ Se ejecuta 1 vez por request (OncePerRequestFilter)

JwtAuthenticationEntryPoint implements AuthenticationEntryPoint
├─ Responsabilidad: Maneja errores de autenticación
├─ Retorna JSON con error
└─ Evita redireccionamiento a login page

UserPrincipal implements UserDetails
├─ Responsabilidad: Adapta User entity a Spring Security
├─ Contiene:
│  ├─ id, username, email, password
│  ├─ authorities (roles como GrantedAuthority)
│  ├─ enabled, accountNonExpired, accountNonLocked, ...
│  └─ Métodos: getUsername(), getPassword(), getAuthorities()
└─ Se crea en CustomUserDetailsService

CustomUserDetailsService implements UserDetailsService
├─ Responsabilidad: Carga UserDetails para autenticación
├─ Métodos:
│  ├─ loadUserByUsername(String) - Busca por username
│  ├─ loadUserById(Long) - Busca por ID (para JWT)
│  └─ Retorna UserPrincipal
└─ Lo llama: JwtAuthenticationFilter y AuthenticationManager


CAPA 5: CONFIGURACIÓN (Config)
━━━━━━━━━━━━━━━━━━━━━━━━━━━━
Ubicación: config/

SecurityConfig (@Configuration)
├─ passwordEncoder() Bean
│  └─ BCryptPasswordEncoder (hashing de contraseñas)
├─ authenticationProvider() Bean
│  ├─ DaoAuthenticationProvider
│  ├─ Usa CustomUserDetailsService
│  └─ Usa BCryptPasswordEncoder
├─ authenticationManager() Bean
│  └─ Maneja autenticación
├─ corsConfigurationSource() Bean
│  ├─ Permite requests desde http://localhost:4200
│  ├─ Métodos: GET, POST, PUT, DELETE, OPTIONS, PATCH
│  └─ Headers: * (todos)
└─ filterChain() Bean
   ├─ Define qué requests requieren autenticación
   ├─ Añade JwtAuthenticationFilter
   ├─ Configura CSRF deshabilitado
   └─ Establece SessionCreationPolicy.STATELESS (sin sesiones)

AuditingConfig (@Configuration)
├─ auditorProvider() Bean
│  ├─ Implementa AuditorAware<String>
│  ├─ Obtiene username del SecurityContextHolder
│  ├─ Retorna "SYSTEM" si no autenticado
│  └─ Llena createdBy/updatedBy automáticamente
└─ Usado por @CreatedBy y @LastModifiedBy

OpenAPIConfig (@Configuration)
├─ Configura Swagger/OpenAPI documentation
├─ Define info: título, descripción, versión
├─ Configura seguridad: Bearer Token
└─ Endpoints visibles en /swagger-ui.html y /v3/api-docs

├─ UserDTO - Data a enviar al frontend (sin password!)

6. CÓMO EXPLICARLO EN UNA ENTREVISTA
================================================================================

ESTRUCTURA RECOMENDADA DE EXPLICACIÓN:
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

1️⃣ PITCH INICIAL (30 segundos)

"He construido un backend empresarial con Spring Boot 3.2 que es una
aplicación J2EE (Java Enterprise Edition). Es una arquitectura de capas
con autenticación JWT stateless, integrada con PostgreSQL y con auditoría
automática de cambios. Los usuarios se pueden loguear, obtienen un JWT,
y luego acceden a endpoints protegidos con control de roles."


2️⃣ ARQUITECTURA DE CAPAS (1-2 minutos)

"La estructura sigue un patrón de capas:

- PRESENTACIÓN: Controllers que exponen los endpoints REST
  AuthController para login/logout/refresh
  AdminController para operaciones admin (solo ROLE_ADMIN puede acceder)

- LÓGICA DE NEGOCIO: Services que contienen la lógica
  AuthService maneja autenticación y generación de JWT
  UserService accede a datos de usuarios
  AuditLogService registra acciones

- ACCESO A DATOS: Repositories que hablan con la BD
  Extienden JpaRepository para CRUD automático
  Tienen queries custom con @Query

- SEGURIDAD: Componentes especiales
  JwtTokenProvider que crea y valida JWTs
  JwtAuthenticationFilter que intercepta requests
  CustomUserDetailsService que carga usuarios

- CONFIGURACIÓN: Beans de Spring
  SecurityConfig que define la política de seguridad
  AuditingConfig que proporciona auditoría automática"


3️⃣ FLUJO DE AUTENTICACIÓN (2-3 minutos)

"El flujo de login es así:

1. El usuario envía username/password a POST /api/auth/login

2. AuthService valida con AuthenticationManager:
   - Busca el usuario en BD por username
   - Usa BCryptPasswordEncoder para comparar contraseñas
   - Si es correcto, crea un objeto Authentication

3. JwtTokenProvider genera un JWT:
   - Incluye el userId como subject
   - Incluye username y roles como claims
   - Está firmado con HMAC-SHA256
   - Expira en 24 horas
   - Se calcula con: exp = now + 86400000 ms

4. Se crea un Refresh Token:
   - UUID aleatorio guardado en BD
   - Expira en 7 días
   - Sirve para generar nuevo access token sin re-autenticar

5. AuditService registra el LOGIN en la tabla audit_logs

6. Se devuelve al cliente:
   {accessToken, refreshToken, userId, username, roles}

7. El cliente guarda en localStorage

Luego, para requests protegidos:
1. Cliente envía: Authorization: Bearer <jwt>
2. JwtAuthenticationFilter lo intercepta
3. Valida la firma del JWT
4. Extrae userId del subject
5. Carga UserDetails de la BD
6. Crea Authentication token
7. Guarda en SecurityContextHolder
8. Request procede normalmente"


4️⃣ SEGURIDAD Y PROTECCIONES (1-2 minutos)

"Las medidas de seguridad son:

AUTENTICACIÓN:
- Contraseñas hasheadas con BCrypt (no reversible)
- JWTs firmados criptográficamente
- Refresh tokens rotatorios (7 días)

AUTORIZACIÓN:
- @PreAuthorize("hasRole('ADMIN')") en endpoints sensibles
- SecurityContextHolder verifica roles antes de ejecutar

STATELESS:
- SessionCreationPolicy.STATELESS
- No se usan sesiones en servidor
- Todo en tokens JWT

CORS:
- Solo requests desde http://localhost:4200
- Headers específicos permitidos
- Previene ataques cross-site

VALIDACIÓN:
- Bean Validation en DTOs
- GlobalExceptionHandler captura errores
- Mensajes de error genéricos (no expone detalles)"


5️⃣ AUDITORÍA (1 minuto)

"Para auditoría tengo:

ENTIDADES CON AUDITORÍA:
- Todas extienden AuditableEntity
- Automáticamente cuelgan: createdAt, updatedAt, createdBy, updatedBy
- Se actualiza automáticamente gracias a @EntityListeners

TABLA AUDIT_LOGS:
- Registra cada acción: LOGIN, CREATE, UPDATE, DELETE
- Quién: username
- Qué: entityType + entityId
- Cuándo: timestamp
- Desde dónde: ipAddress
- Detalles adicionales

AuditorAware Bean:
- Extrae el username del SecurityContextHolder
- Lo asigna automáticamente a createdBy/updatedBy
- Si no está autenticado, pone 'SYSTEM'"


6️⃣ BASE DE DATOS (1 minuto)

"Uso PostgreSQL con Hibernate/JPA:

ESTRUCTURA:
- Tabla users: username (UNIQUE), password, role, email, etc.
- Tabla refresh_tokens: token UUID, user_id (FK), expiryDate

MIGRATIONS:

USER DTO (enviado al cliente):

PREGUNTAS TÍPICAS Y RESPUESTAS:
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

P: ¿Por qué JWT en lugar de sesiones?
R: Los JWTs son stateless. El servidor no necesita almacenar sesiones,
   lo que facilita escalabilidad horizontal. Cada request es autónomo.
   El cliente lleva toda la info de autenticación en el token.

P: ¿Cómo se protege el JWT?
R: Se firma con HMAC-SHA256 usando una clave secreta en el servidor.
   Si alguien intenta modificar el payload, la firma ya no coincide.
   Además, expira en 24 horas.

P: ¿Qué pasa si se roba un JWT?
R: Es un riesgo. Por eso se transmite sobre HTTPS (en producción).
   Por eso expira rápido (24 horas).
   Por eso hay refresh tokens separados para renovar.
   En logout invalida refresh tokens en BD.

P: ¿Cómo funciona el refresh token?
R: El access token expira en 24 horas. Si el usuario aún está activo,
   puede usar el refresh token para obtener uno nuevo sin volver a
   autenticar. El refresh token tiene 7 días de validez.

P: ¿Por qué BCrypt para contraseñas?
R: BCrypt es un algoritmo adaptable con salt aleatorio. Es lento a propósito
   (computacionalmente costoso), lo que dificulta ataques de fuerza bruta.
   Nunca se pueden recuperar las contraseñas originales.

P: ¿Cómo maneja la auditoría?
R: AuditableEntity proporciona createdAt, createdBy, updatedAt, updatedBy.
   AuditorAware Bean extrae el username del SecurityContextHolder.
   AuditLog tabla registra acciones específicas (LOGIN, UPDATE, DELETE).
   Todo automático sin código boilerplate.

P: ¿Cómo escalas esto?
R: Por ser stateless con JWT:
   - Múltiples instancias sin compartir sesiones
   - Load balancer puede enviar requests a cualquier instancia
   - BD debe ser compartida (PostgreSQL en servidor común)
   - Redis para cache si hay mucho tráfico

P: ¿Y si la contraseña es débil?
R: Bean Validation puede validar según reglas.
   Pero aquí solo tenemos login.
   En producción: requerir mayúsculas, números, símbolos, min 8 chars.

P: ¿Cómo funciona @PreAuthorize?
R: Spring Security evalúa la expresión SPEL.
   "hasRole('ADMIN')" busca 'ROLE_ADMIN' en authorities del usuario.
   Si no está, retorna 403 Forbidden antes de ejecutar el método.

P: ¿Qué es MapStruct?
R: Framework que genera mappers Entity ↔ DTO en compile-time.
   No usa reflection, es muy rápido.
   Configurable con @Mapping para rename/transform.

P: ¿OncePerRequestFilter vs Filter?
R: OncePerRequestFilter garantiza que se ejecuta exactamente 1 vez por request.
   Filter normal podría ejecutarse múltiples veces si hay forward/include.
   Importante para JWT porque queremos validar una sola vez.

P: ¿Cómo es el flujo de error?
R: Exception ocurre en un endpoint.
   GlobalExceptionHandler @ExceptionHandler la captura.
   Retorna ResponseEntity con ErrorResponse JSON.
   Cliente recibe status code (404, 401, 400, etc.) y mensaje.

P: ¿Transacciones @Transactional?
R: Login usa @Transactional porque hace múltiples operaciones:
   - Autentica (lee BD)
   - Genera JWT
   - Crea RefreshToken (escribe BD)
   - Registra AuditLog (escribe BD)
   Si algo falla, todo se revierte (rollback).
